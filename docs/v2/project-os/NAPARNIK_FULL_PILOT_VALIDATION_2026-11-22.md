## Что выявили промежуточные проверки

Транспортный тест выявил `TypeError` для не-ASCII webhook secret вместо HTTP 401;
сравнение исправлено и регрессия проходит. Первый сквозной тест содержал два
дефекта самого тестового окружения: замена объекта worker не затрагивала closure
drain, а legacy fixture использовал неверное имя столбца. Исправлены без изменения
поведения ради прохождения теста.

Сквозная проверка воспроизвела падение worker при отключении темы. Отключённый
scope теперь возвращает неактуальную задачу и отменяет очередь, включая отключение
во время AI-вызова. Первый общий прогон дал 1112 passed / 4 failed во время
согласования нового `experiment_id` в контракте worker/repository и scope-off
guards. После согласования контрактов выполнен общий успешный прогон выше.

Последняя сверка с исходным требованием выявила поведенческое несоответствие:
предварительный `SILENCE` по текущему пригодному отчёту мог завершить обработку до
исторической выборки. Теперь ранний выход применяется только к непригодному для
разбора материалу; каждый подходящий отчёт получает окончательное решение после
разрешённой памяти. Добавлены два regression-сценария: сохранение молчания и
появление полезного вопроса после истории. После исправления выполнен финальный
общий прогон **1140 passed**. Режим одной фазы `index` сохранён.

Независимое чтение кода также выявило и помогло исправить:

- transient текущий запрос мог участвовать в сохранённом эксперименте без полного
  набора долговременных источников;
- ID эксперимента не был показан участнику;
- `/track_delete` неожиданно удалял исходный архив;
- меню `/stop` обещало более широкий отзыв разрешений, чем выполнял код;
- TTL-очистка могла перестать работать для темы, удалённой из конфигурации;
- смена статуса эксперимента и удаление трека должны отменять ответы, подготовленные
  по прежнему производному состоянию;
- новый runtime должен отказывать при попытке использовать базу другого приложения
  или перехватить чужой уже настроенный webhook;
- права, актуальность transient запроса и scope нужно проверять перед каждой
  платной фазой, а все предоставленные модели источники — ещё и при отправке.

## Покрытие сквозного сценария

Доставленное уведомление → личные разрешения → сохранение отчёта → анализ →
проверяемый ответ → прямой запрос → подтверждённый обзор/трек → удаление.
Отдельно проверены AI off, provider timeout, денежный предел до запроса, молчание
при сохранённом отчёте, индексация без публикации, иной автор/тема, вложенный чужой
reply, отзыв после генерации, неоднозначная отправка и повтор webhook после rollback.

Для эксперимента проверены три настоящих PostgreSQL-сценария с fake transport:
успешная отправка, неоднозначный результат и отзыв разрешения. Только успешная
отправка переводит `prepared` в `offered`. Принятие и попытка остаются разными
статусами, опирающимися на отдельный собственный источник участника.
