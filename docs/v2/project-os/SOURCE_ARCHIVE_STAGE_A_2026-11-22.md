# Stage A — разрешённый архив полученных источников

**Дата:** 2026-11-22. **Контракт:** [issue #168](https://github.com/Mix13131/nenoybot/issues/168).
**База реализации:** `v2@805d2aafc709cb2323f228d791b16bb1f63f64b8`.
**Разрешение владельца в текущей сессии:** изолированная реализация, синтетические тесты, отдельная ветка и Draft PR. Это не принятие G1/G8, не разрешение G9 и не согласие участников на реальное хранение.

## Результат и границы

Stage A сохраняет полученный источник независимо от решения отвечать, доступности AI и разрешений на анализ. Источник имеет точного автора, группу, тему, время создания, время редактирования, отдельные версии, стабильный `source_id` и SHA-256. Поиск работает без AI.

Ветка: `feat/stage-a-source-archive-20261122`, Draft PR направляется в `v2`. Нет изменений legacy `app/`, `tests/`, CI, Railway, действующих групп или рабочей БД. Номер миграции `0010` проверен относительно `0001–0009` и открытых PR #95, #142–147, #150, #156; конфликтов миграций не найдено.

Это первый работающий слой памяти. Семантические выводы, наставник, персональный трек, самостоятельные ответы и платные AI-вызовы относятся к Stage B. У PR #164 остаётся замечание о едином конкурентно безопасном резервировании денег **перед каждым** платным вызовом; Stage A не вызывает платные модели и не заявляет исправление этого замечания.

## Как проходит запись

`normalize_update` → строгая проекция Telegram-источника → точная группа/тема → индивидуальное `retain_source` → архив и обычное событие в общей PostgreSQL-транзакции → успешный ответ webhook.

Ошибка архива откатывает принятие события. Ошибка обычного ingest после записи архива также откатывает архив. После повторной доставки одна версия сохраняется ровно один раз. Архивирование расположено до классификации отчётов, диспетчера ответов, вызовов модели и проверки её бюджета.

По умолчанию функция выключена. `NENOY_V2_SOURCE_ARCHIVE_ENABLED=1` — только технический флаг; дополнительно нужны включённая строка **точной темы** и отдельный grant автора. Миграция создаёт пустые таблицы и никого не подключает. Наличие обычного whitelist/group profile не предоставляет архивного разрешения.

Новые таблицы:

| Таблица | Назначение |
| --- | --- |
| `source_archive_scopes` | Явно настроенные forum topics и момент активации |
| `source_archive_consents` | Текущие независимые разрешения каждого автора в каждой теме |
| `source_archive_consent_versions` | История версий разрешений и границ хранения |
| `source_archive_deletions` | Запросы удаления конкретных сообщений, включая ещё не полученные |
| `source_archive_messages` | Неизменяемые автор/тема/время сообщения, указатель последней правки, tombstone |
| `source_archive_revisions` | Все принятые версии, происхождение, покрытие, checksum и статус удаления |

Архив не зависит от lifetime строки `events` или обычного `messages.text`. Текущая очистка обычного текста через 30 дней остаётся прежней и не затрагивает новые таблицы.

## Пять отдельных разрешений

| Разрешение | Поведение Stage A |
| --- | --- |
| `retain_source` | Разрешает архивировать источники только этого автора в этой теме |
| `historical_inference` | Дополнительно открывает источник для будущего исторического анализа |
| `auto_report_analysis` | Хранится независимо; анализа в Stage A нет |
| `unsolicited_group_reply` | Хранится независимо; самостоятельной отправки в Stage A нет |
| `direct_request_group_reply` | Хранится независимо; не даёт права показывать чужой архив |

`set_permissions` заменяет явный набор пяти флагов целиком. Разрешение хранения не включает остальные четыре. `actor_user_id` должен совпадать с автором; роль администратора не заменяет согласие участника.

Это внутренний repository API. Будущий Telegram-интерфейс согласия обязан получать actor из аутентифицированного update; принимать actor ID из недоверенного запроса нельзя. В этом PR нет публичного endpoint, команды массового подключения, реальных grants или пользовательского интерфейса согласий.

## Поддержка источников — версия 1

| Источник | Содержимое архива | Покрытие |
| --- | --- | --- |
| Обычный текст, включая беседу и отчёт | Исходный текст без сокращения | `full` для текста |
| Подпись к фото/видео/документу | Исходная подпись и доступная ссылка на файл | `partial` |
| Голосовое/фото/документ без подписи | Тип и разрешённые file references; без байтов | `unavailable` |
| Прочие поддерживаемые события с неизвестным телом | Честный тип/признак отсутствующего тела | `unavailable` |
| Правка сообщения | Отдельный source ID и revision; старая версия сохраняется | По типу содержимого |
| Forward / Telegram quote / blockquote | Тело текущего полученного сообщения, external-content marker | Исключено из historical inference |
| Вложенный `reply_to_message` | Только ID ответа; чужой вложенный текст не копируется | Не становится отдельным источником |
| Личный чат, канал, бот, `sender_chat`, неизвестная тема, ephemeral/limited-audience message | Не сохраняется | Fail closed |

Для forum source обязательны `supergroup`, `is_forum=true`, `is_topic_message=true` и положительный `message_thread_id`. Тема не выводится из текста, названия или вложенного сообщения. General без явного thread ID не поддерживается этой версией.

Используются отдельные `occurred_at` и `revision_at`. `message_revision` — номер принятой версии, а не доказательство порядка Telegram-правок. Latest выбирается по времени правки и update ID; поздно доставленный оригинал не заменяет более новую правку.

Telegram-время имеет точность до секунды. Граница активации/grant округляется **вверх** до целой секунды и видна в `coverage().eligible_since`. Сообщения той же неполной секунды не считаются разрешёнными задним числом. При повторном включении темы устанавливается новая граница; правки сообщений, созданных до действующей границы, не импортируют старую историю.

Описание полей источника: [Telegram Bot API — Message](https://core.telegram.org/bots/api#message). Произвольную цитату, набранную обычным текстом, нельзя достоверно распознать этим адаптером. Stage A не выполняет семантическое определение авторства утверждений и не делает выводы о третьих лицах.

## Получение и проверка источников

`query_sources` всегда требует группу, тему, автора, actor, диапазон дат и цель. Возврат ограничен страницей до 200 строк; это размер страницы чтения, не квота на полезные сообщения или на архивирование. Даты задают полуинтервал `[since, until)`.

- `owner_export`: только собственные источники; может показать историю правок.
- `historical_inference`: дополнительно требует текущий grant; исключает forward/quote и superseded revisions. `history=true` для этой цели запрещён.
- Групповой endpoint выдачи архива не добавлен. Ни один путь не обращается к Personal memory.

Latest-пагинация использует неизменяемые время создания и message ID: правка уже просмотренного сообщения не возвращает его повторно. История использует стабильные version source IDs. Пагинация не обещает фиксированный снимок при одновременном поступлении ещё неизвестных старых сообщений; будущий массовый экспорт при активной записи должен явно выбрать snapshot semantics.

`reauthorize` перепроверяет точную область, latest-version, checksum, текущий consent version и статус. Редактирование, удаление, отключение темы и изменение разрешения инвалидируют старую выборку. Это примитив проверки источников; он не является правом отправить ответ позже. Stage B обязан выполнить проверку у окончательной отправки и согласовать её с конкурентным отзывом разрешения.

## Удаление и полнота

Отзыв `retain_source` и append сериализуются блокировкой одной строки consent. Отзыв очищает текст, media references и checksum всех текущих версий этого автора/темы, оставляя технические tombstones. Известный удалённый message ID не восстанавливается при повторной доставке или новой правке.

`forget_sources` с message ID удаляет конкретное сообщение и сохраняет scoped deletion intent, даже если сообщение ещё не получено. Квитанция отдельно показывает `deletion_intent_recorded=true`; число очищенных записей в этом случае честно равно нулю. Последующая доставка этого автора/темы/message ID не восстановит тело. Чужой автор или другая тема с тем же числовым message ID не затрагиваются. Если для автора/темы вообще нет consent record, такой запрос явно отклоняется. Удаление всей области дополнительно создаёт новую временную границу и версию согласия: ещё не полученное старое сообщение не может восстановить забытый период. Разрешения на будущие сообщения сохраняются. Повторное предоставление хранения после отзыва также не импортирует историю задним числом.

Квитанция сообщает точную область `reflection_source_archive_only` и числа очищенных живых сообщений/версий. Она **не** заявляет удаление обычных legacy stores, уже отправленных сообщений Telegram, старых backup или физических следов PostgreSQL. Глобальная команда «забудь меня» с обходом всех остальных хранилищ относится к следующему отдельному интеграционному решению.

`coverage` показывает разрешённую границу, количество источников/версий, удалённые и неполные версии, первый/последний полученный источник. Оно всегда явно сообщает:

- известны только фактически полученные разрешённые события;
- пропуски доставки и незафиксированные интервалы простоя могут быть неизвестны;
- прежняя Telegram-история и media bytes не импортировались;
- автоматическое обнаружение удаления обычного группового сообщения в Telegram не реализовано.

Нельзя называть этот архив полной историей жизни участника или всей историей Telegram-группы.

## Проверки и воспроизводимость

Используются реальные PostgreSQL-транзакции и только синтетические данные. Базовая ветка до изменений: `768 passed`, без skips. Первоначальная проверка нового кода обнаружила два устаревших списка ожидаемых миграций `[7,8,9]`; они обновлены до `[7,8,9,10]`, сохранены остальные assertions onboarding.

Основная команда для существующего тестового PostgreSQL:

```bash
NENOY_V2_ENV=test NENOY_V2_TEST_DATABASE_URL='<isolated-test-postgresql-url>' \
  python -m pytest tests_v2 -q

Первый полный прогон: **883 passed, 0 failed, 0 skipped**, 21.88 s, включая 115 новых проверок. Внешнее GitHub Codex review затем выявило P2: запрос удаления ещё не полученного конкретного сообщения не сохранял намерение удаления. Добавлен scoped marker и отдельные регрессионные проверки. Итоговый повтор, commit SHA и результат повторного ревью фиксируются в Draft PR, чтобы отчёт ссылался на проверенный HEAD.

100k fixture загружается bulk SQL для проверки retrieval; он не выдаётся за 100k webhook calls. Permission/capture/transaction paths проверены отдельными сценариями. Bulk load выполняет `ANALYZE`, чтобы PostgreSQL имел статистику для FK/reader plans. Полный экспорт 25k может использовать последовательные проходы; SLA интерактивного поиска по результатам этого синтетического теста не объявляется.

Отдельно выполнен `tests_v2/manual/archive_backup_restore_smoke.py` через тот же fresh PostgreSQL runner и `--pg-bin`: **PASS**, exit 0. Настоящие `pg_dump`/`pg_restore` восстановили текст/checksum активного источника, tombstone удалённого и marker ещё не полученного сообщения. Replay, поздняя новая правка и первая задержавшаяся доставка удалённого сообщения после восстановления не вернули текст. Копия сделана **после удаления**; проверка не заявляет очистку старых backup. Script принимает только пустую loopback-БД `nenoy_v2_test` с явным `NENOY_V2_ENV=test` и удаляет только собственную временную restore-БД/файл.

Промежуточные ошибки проверки не скрыты: исходная машина не имела `pytest`; окружение подготовлено отдельно от runtime. Первый bulk fixture без `ANALYZE` упёрся в медленный план FK; исправлена подготовка синтетических данных. Первоначальное требование конкретного индекса для широкого export оказалось неверным предположением о выборе планировщика: широкий обход проверяет полный правильный результат, а индекс доказан на фактическом запросе с узким диапазоном дат. Конечные проверки выполнены заново на свежей БД.

## Откат и следующий gate

Рабочий обратимый откат: выключить флаг архива и вернуть прежнюю версию кода. Новые таблицы и сохранённые источники при этом не удаляются. Не запускать DDL downgrade на архиве с данными. В тесте проверено только удаление пустой изолированной схемы в правильном порядке; обычные таблицы остаются целыми.

Перед реальной активацией остаются отдельными решениями: точные группа/темы, подтверждённые личные grants, пользовательское объяснение baseline retention, срок хранения нового архива, права DB/backup, шифрование, контроль роста, процедура удаления и восстановления с повторным применением отзывов после старого backup. Синтетическое восстановление свежей копии не доказывает готовность этой operational policy.

**Следующий gate:** независимое ревью точного Draft PR HEAD и человеческая приёмка результата Stage A. Merge, рабочая миграция и включение реальных участников требуют отдельного разрешения.
